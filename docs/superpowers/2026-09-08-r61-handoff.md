### 5b. PROPOSED — that after R185, the rest of the release is mechanical

This is the prediction the release loop is really built on, and it **must be RUN before anything is
planned around it.** `RELEASE.md` is a six-step checklist and steps 3–6 look mechanical. Four things
under them are unverified, and any one of them turns "a release loop" into two:

1. **The full suite** (`pytest -q`) — the run started in this loop was still going when this was
   written; part 1 records where its result lands. ~60 minutes.
2. ~~**`mkdocs build --strict`**~~ — **RUN 2026-09-08, and it PASSES**: *Documentation built in
   0.75 seconds*, no strict failure. (The red block Material prints is its own upstream banner about
   MkDocs 2.0, not a build error — do not read it as one.) This item is discharged; the nav is
   intact. It is left in the list struck rather than deleted, because the next three are not.
3. **The promotion queue** (`RELEASE.md` step 1) — how many wiki pages are queued, and which are
   worth promoting, is a judgment nobody has made. The queue is *"the visible, enumerable lag …
   not a blocker"*, so this can be scoped to zero deliberately — but that should be a decision, not
   an omission.
4. **The PyPI Trusted Publisher.** `RELEASE.md` calls it a *one-time prerequisite, manual, on
   pypi.org*, and nothing in the repo can verify it. If it was never configured, the tag build
   deploys the site and then **fails at the publish step with an OIDC error**. Worth confirming with
   the account owner *before* tagging, because it is the one failure that happens after the
   irreversible act.

**If 5b survives contact, the release is one loop. If item 2 or 4 fails, it is two.** Budget for
two and be pleasantly surprised; do not write a plan that assumes one.

A release asserts something about what iladub can do, and this project's own epistemics (CLAUDE.md
