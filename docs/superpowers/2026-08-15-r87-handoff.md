### 3.2 Spec §4.3's first bullet does not do what §M3 says — this is the big one

The spec says to add `risk.ttl` to the ontology graph built by `_build_membrane`, on the
premise (M3, spec lines 43-47) that `risk:order` is invisible because `risk.ttl` is absent from it.

Measured, that premise is wrong:

- `membrane._payload_nt` uses `ont_graph` for exactly one call — `subclass_closure(data_graph,
  ont_graph)` (`membrane.py:331`). The ontology is never merged into the validated artifact;
  `subclass_closure`'s docstring says so at `membrane.py:451`.
- `subclass_closure` reads `ont_graph` for `rdfs:subClassOf` triples only (`membrane.py:477`).
- `grep -c "subClassOf\|subPropertyOf" vocab/ontology/risk.ttl` → **0**.

So `risk.ttl` in `_FULL_ONT` contributes nothing to the payload, `?sev risk:order ?so` still binds
nothing, and `dec:EscalationShape` stays vacuous. A subagent reached the same conclusion
independently and demonstrated it end to end on a minimal leak graph: ont-without-risk conforms,
ont-with-risk conforms, **risk.ttl merged into the DATA graph refuses**. The existing escalation
tests already take the data-graph route (`tests/test_escalation_shacl.py:31,37`,
`tests/test_escalate.py:69`).

**Consequence for the plan:** `risk:order` must reach the *data* graph, not `_FULL_ONT`. Where and
how is a design decision this handoff does not make.

### 3.4 There are two `_validate` call sites, not one

Spec §4.1 says the derived triples must be in the graph before `compile._validate` runs. That names
two sites, not one:

- `compile.py:1083`, page scope, gated at `:1079-1082` on the page carrying a `tab:RecordTable` or
  `tab:HierarchicalTable`.
- `document.py:1516`, document scope, gated at `:1515` on `recognized or section_facts`.

### 3.5 The `datagrid_adopt` path rebuilds the page graph and drops the decisions

`compile.py:1027` does `graph = Graph()`. `ReadingRecorder` was bound to the *original* graph object
at `compile.py:488`. On an adopting page the verdict decisions are therefore absent from the graph
`_validate` receives. Furnishing placed at the recording site would be discarded exactly there —
the same shape as R73's defect 2, which CLAUDE.md rule 2 exists to catch.

### 3.6 `dec:escalatedTo`'s declared range contradicts the derivation

`dec:escalatedTo` declares `rdfs:range dec:DecisionHolon` (`dec.ttl:213`). The spec derives
`?d dec:escalatedTo ?req` with `?req a dec:ExpansionRequest`, and `dec:ExpansionRequest
rdfs:subClassOf dec:Event` (`dec.ttl:198`) — not `dec:DecisionHolon`.

Nothing catches this: `subclass_closure` does no range typing, which is also what keeps R69 shut.
The precedent fix is one line away in the same file — `dec:regarding` was widened to
`owl:unionOf (dec:DecisionHolon dec:ExpansionRequest)` at `dec.ttl:204` for this exact reason.
Not applied; the plan should decide.

### 3.7 Spec §5's O1 needs a stricter oracle than "a document that escalates"

§5 names apple, bfs, cbh-stem and who-wfa. Escalating is not sufficient — the page must also reach a
membrane (§3.4). Measured per page: **apple p1, bfs p0 and bfs p4 escalate but carry neither table
type**, so `_validate` is never invoked on them and they pin nothing.

Best oracle measured: **`bfs-population-bilan-2023` page 5** — 6 escalated decisions (the highest of
any single corpus page), carries `tab:RecordTable` (`…/p5#ttable13`) so the gate fires, 5.7s to
compile, and no second-pass complication. Its decisions are `…/p5#region{2,7,9,10,11,12}-d{4,5}`.
Avoid cbh-stem p0: it compiles twice and mints tables under both `…/p0#` and `…/p0/r2#`.
