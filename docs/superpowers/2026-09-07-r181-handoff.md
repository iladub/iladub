### 5a. PROPOSED — [[R182]]: measure the two things that decide whether the shape is buildable AT ALL

Proposed, not asserted, because **the work is contingent on two facts neither measured nor
obviously true**, and if either goes the wrong way the loop R182 imagines is not the loop to run:

1. **Is there an edge from a `tab:LabelCell` to the `tab:HeaderSourceCell`s it was joined from?**
   A containment shape needs a `sh:path` to walk. `prov:wasDerivedFrom` exists in this area but
   points a *repeated* header row at its originating source cells (`vocab/ontology/tab.ttl:443`) —
   a different edge for a different purpose. If no label→source edge exists, R182 is first a graph
   change and only then a shape, which is a materially bigger loop than "add a shape".
2. **Does putting `tab:hasBBox` on a `tab:HeaderSourceCell` RDFS-type it as a `tab:Cell` and trip
   `tab:WrappedCellShape` at the tiling gate?** That is the R19 mechanism, and this repo has
   already paid for it once: `tab:markerRegion` exists as a separate property *precisely* to dodge
   it (`compile.py:227`, `tab.ttl:545`). `HeaderSourceCell` is inside the gate — it is
   `tab:HeaderContentConservedShape`'s target — so a naive `hasBBox` could refuse readings that
   pass today.

Both are cheap: (1) is a graph dump on graincorp-stem p0, (2) is adding the triple in a scratch
graph and running `region_tiles`. **Measure both before designing anything** — this loop's own
history is the argument, since R181's prescribed suspects were both wrong and cost nothing to
refute only because the instrument was run first.

**Disposal, when it is built:** a shape that FAILS on today's graincorp-stem p0 emission with this
loop's union reverted, and PASSES with it. That is a real falsification, not a green-on-green.
