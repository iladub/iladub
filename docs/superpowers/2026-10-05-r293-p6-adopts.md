## 1. Goal

Find why bfs p6 adopts no data grid. #309's handoff predicted that, if p6 adopted, its existing
boxhead recording would label the columns and remove both [[R293]] symptoms with no new reader.

## 2. Findings (measured on `bfs-canton-boxhead` `d4d71c8`)

### 2.1 The grid derives. The ordinal refuses it, and would refuse even a perfect one.

`derive_data_grids(pdf, 6)` returns one grid of 32 rows × 9 columns, with lines 7–38 as rows. So
the handoff's fear that a page split nine ways would refuse at derivation is false.

`compile_tables(pdf, 6, datagrid_adopt=True)` opens the gate, because the bands escalate 19
tokens (band 1, the title, 16, `KIND_NOT_SUPPORTED`; band 11, the footnotes, 3,
`REGION_TILING_FAILED`). It then refuses at the ordinal (`compile.py`, `_led.escalated_tokens <
escalated_total`). With `build_ledger` instrumented:

```
band 1  escalated esc 16 lines [1, 2]          (title; the grid does not touch it)
band 2  asserted  esc 0  lines [3, 4, 5, 6]    touched   <- the boxhead, read as a record table
band 3..10 asserted esc 0                      touched
band 11 escalated esc 3  lines [39, 40, 41]    (footnotes; untouched)
ledger escalated 44, residue (3, 5, 6)         vs the bands' 19 -> refused
```

**A perfect boxhead read could not adopt either.** If every header line were carried, the residue
would be empty and the grid would leave 16 + 3 = 19 unread. That ties the bands' 19, and the
ordinal is strict. The bands' defect is ink they assert **wrongly** (lines 4–6 as entry cells,
which is [[R293]]), and an ordinal over **unread** ink cannot see a misreading.

### 2.2 The residue has two causes

- **Line 3 is not carried because column 6 is dropped.** `dispose_boxhead` placed each label word
  by its own centre. `80` (x 383.4–390.3, centre 386.9) falls left of column 6's derived edge at
  389.1, so the label `80 ans ou plus` was refused, although as typeset it sits in column 6
  (383.4–~425). One unplaced label leaves the whole line uncarried (`carried_lines` is
  line-granular).
- **Lines 5 and 6 are not carried because of footnote marks** `1` and `2`. The prompt sends
  footnote marks to `other_words` by design (`baml_src/boxhead.baml:38,62`). That is honest: the
  marks are not labels, and their 6 tokens stay residue. Not changed.

### 2.3 Change 1: place a label by its ink on each line, not by each word

`boxhead.dispose_boxhead`: a leaf label is admitted when, **on each line it occupies**, the
centre of its ink there (`min x0`…`max x1` of its words on that line) lies in the column's
interval. A label is typeset as one run per line, so the run is the unit.

**It only admits more.** Take a line fragment whose words all have centres in `[x0, x1)`. Its
centre is `(min x0 + max x1) / 2`. That is at least the first word's centre (since `max x1 ≥` the
first word's `x1`) and at most the last word's centre (since `min x0 ≤` the last word's `x0`), so
it lies in the interval too. No label admitted today is refused. No constant was added.

### 2.4 Change 2: an answer above 1 escalates the record region instead of asserting it

`_header_lines_decision` returns the reader's `k`. Where `k > 1`, the record path, which carries
one header level, **escalates the region** (`BOXHEAD_EXCEEDS_RECORD`) instead of asserting lines
2..k as entries. Box-split spec § 10.6 had the emission take 1 for any `k > 1`. That asserts as
data what the record path's own reader called header: a proposition passing as an assertion
(CLAUDE.md § 3). This note revises § 10.6's third bullet.

**Blast radius, measured offline.** `readings/header_lines/` holds 7 recordings. Exactly one
answers above 1: `c71008e113…` (`k = 3`), whose note names p6's age groups and dependency ratios.
With no live reader, no other region can reach the new branch.
