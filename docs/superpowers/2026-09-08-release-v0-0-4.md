## 0. What the R185 handoff asked

Two things. **5a**, asserted: run `RELEASE.md` steps 1 and 3 — the promotion queue (a judgement
nobody had made) and the version bump. **5b**, proposed: *"the PyPI Trusted Publisher … Manual, on
pypi.org, and **nothing in this repo can verify it**. … Confirm it with the account owner BEFORE
tagging — this is the single item that makes the difference between one loop and two, and it
cannot be measured from here."*

**5b is wrong on its load-bearing clause, and this is the finding worth keeping.** It *can* be
measured from here, in one call, without the account owner — because the last release already ran
the step:

```
$ gh run list --workflow=release.yml --limit 5 --json conclusion,headBranch,createdAt
[{"conclusion":"success","createdAt":"2026-08-02T03:20:29Z","headBranch":"v0.0.3", …}]

$ gh run view 30730453507 --json jobs -q '.jobs[].steps[] | …'
… "Publish to PyPI (trusted publishing; no-op if version exists)=success" …

$ curl -s https://pypi.org/pypi/iladub/json | …
latest 0.0.3   releases ['0.0.1','0.0.2','0.0.3']   upload 2026-08-02T03:24:53
```

The v0.0.3 tag build's publish step **succeeded**, and PyPI's own upload timestamp
(`03:24:53`) sits four minutes after that run started (`03:20:29`). Trusted publishing was
configured and exercised. The handoff asked for a human confirmation of a fact the CI history
already asserts.

**What survives of 5b's caution:** the evidence is *historical*. It proves the publisher was
configured on 2026-08-02, not that it is configured now — a Trusted Publisher can be revoked on
pypi.org and nothing here would see it. That residual risk is real and is the same shape the
handoff described (fails *after* the irreversible act, site deployed, publish errored). It is
one order of magnitude smaller than "nobody has ever checked", which is what the row implied.

**The generalisable lesson:** *"nothing in this repo can verify it"* is a claim about the repo's
**files**. The release pipeline's own run history is evidence too, and it is one `gh` call away.
Before writing "unverifiable from here", ask whether the thing has ever run.

## 3. Step 3 — the version bump, and a guard that did not exist

`0.0.3` → **`0.0.4`** across the three files `RELEASE.md` names, with
`CITATION.cff: date-released: "2026-09-08"`.

**`RELEASE.md` step 3 was false, and the falsity was in the direction that matters.** It read:
*"all in lockstep (guarded by `tests/test_smoke.py::test_version_single_source`)"*. Measured, that
test guards **two** of the three:

```python
assert iladub.__version__ == pyproject["project"]["version"]     # the whole test body
```

and `grep -rn CITATION tests/ scripts/ .github/workflows/` returns **nothing** touching the file's
version. `CITATION.cff` — the *citable* record of the release, the artifact CLAUDE.md
§ Authorship / FAIR posture exists for — could drift silently behind the tag, and the manual said
it could not.

Fixed by **adding the guard**, not by weakening the sentence: `test_citation_version_matches`
(`tests/test_smoke.py`) holds `CITATION.cff`'s `version:` against `iladub.__version__`, by regex
rather than YAML so no dependency is added to read a file nothing else reads at runtime.
`RELEASE.md` step 3 now names **two** guards and states plainly that `date-released:` is guarded
by nothing and is set by hand.

### FALSIFICATION

```
$ sed -i '' 's/^version: "0.0.4"/version: "0.0.3"/' CITATION.cff
$ .venv/bin/python -m pytest tests/test_smoke.py::test_citation_version_matches -q
FAILED tests/test_smoke.py::test_citation_version_matches - AssertionError
1 failed in 0.36s
$ sed -i '' 's/^version: "0.0.3"/version: "0.0.4"/' CITATION.cff      # restore
$ .venv/bin/python -m pytest tests/test_smoke.py -q
3 passed in 0.28s
```

The test fails on exactly the drift it exists to catch, and the drift it was given is the real
one — `0.0.3` is what the file carried an hour earlier.

## 5. What §5c asked, and why it does not block this release

The four corpus scores (`graincorp 0.9654 · bfs 0.9401 · WHO 0.9096 · apple 0.6289`) have been
quoted through **five** handoffs now without re-measurement. §5c's rule is *"re-measure before any
of them reaches a published page"*. Measured, none of them does:

```
$ for f in <every page in mkdocs.yml nav>; do grep -cE '0\.[0-9]{3,}' "docs/$f.md"; done
(no page matches)
```

Every quote lives in `docs/wiki/**` (a proposition) or `docs/superpowers/**` (evidence). With the
queue drained to zero, **no wiki page is promoted**, so the tag publishes no score at all. §5c's
condition is not triggered — and it is carried forward unchanged, still unmeasured, in the next
handoff. §1's table above shows the warning was well-founded: two of the four are demonstrably
stale in the page that quotes them.
