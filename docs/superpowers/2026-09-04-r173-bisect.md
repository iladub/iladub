## 1. Method — and the two traps that make a naive re-run report green

The corpus is gitignored (`.gitignore:52`), and the venv's editable install is a `.pth` pointing at
the **main checkout's** `src`. Either one alone makes a worktree run measure the wrong thing.

```
# trap 1 — a fresh worktree has no corpus, so all eight SKIP and the run is green
$ git worktree add "$WT" <commit>
$ ln -s "/Volumes/WD Green/dev/git/iladub/corpus" "$WT/corpus"

# trap 2 — the .pth resolves iladub to MAIN's src, so every probe measures main's code
$ cat .venv/lib/python*/site-packages/_editable_impl_iladub.pth
/Volumes/WD Green/dev/git/iladub/src

# the fix, and the check that it took (PYTHONPATH precedes .pth-added site paths)
$ cd "$WT" && PYTHONPATH="$WT/src" .venv/bin/python3 -c "import iladub; print(iladub.__file__)"
…/bisect-wt/src/iladub/__init__.py          ← the WORKTREE's, not main's
```

The probe, run at each commit, is the three files R173 names — not the eight node IDs, because the
failing *set* is part of what is being measured and node IDs would have hidden the swap in § 5:

```
PYTHONPATH="$WT/src" .venv/bin/python3 -m pytest \
  tests/etkl/test_adoption_document.py tests/etkl/test_escalation_wiring.py \
  tests/test_corpus_stem.py -q -p no:randomly --no-header -rf
```

Four worktrees ran in parallel on 4 performance cores; a probe costs 4–6 minutes wall.
Seven probes were run.

## 5. The result nobody asked for — R173's row is counted right and set wrong

R173's row states, of the R165 branch base `d757279` and the shipped HEAD: *"**8 failed, 22 passed
at BOTH**, with byte-identical failure values … So the one-band merge moves NEITHER."*

The count is right. The **set** is not:

| test | `d757279` (base) | `500274a` (HEAD) |
| --- | --- | --- |
| `test_the_document_score_rises` | **FAIL** | pass |
| `test_an_adopted_page_never_scores_one_by_construction` | pass | **FAIL** |

The R165 one-band merge moves **two** of the eight, in opposite directions, and they cancel in the
count:

- **Repaired.** `test_the_document_score_rises` pins `apple_doc.score >= 0.35560344827586204`. At
  the base it measured `0.18950437317784258`; the one-band merge takes apple to `0.6289`
  (R165's own headline), which clears the floor.
- **Broken.** `test_an_adopted_page_never_scores_one_by_construction` asserts
  `p1.escalated > 0` and `p1.score < 1.0`. At HEAD apple p1 reads
  `CompilationReport(score=1.0, …, asserted=56, escalated=0)`, so it fails `assert 0 > 0`.

**Why the original claim missed it:** R173 compared the 8/22 *counts* and the two *named* failure
values it quoted (`() == (1,)` and the stem score). Both of those are genuinely byte-identical at
base and HEAD. The two that swapped are neither of them. **A count is not a set**, and this is the
worked case.

**What it means, and what it does not.** It does not overturn R173's substance: the class of
failure predates the branch, and six of the eight are untouched by the merge. It does overturn one
clause, and one that a next session would have relied on. The new failure is also **not** a stale
fixture — the test is the "zeroing tautology, refused" guard, and it is firing on a page that
reached `score=1.0` **without** adopting anything (`adopted == ()`). Whether apple p1's 56 asserted
cells are the correct reading is [[R172]]'s open question, and this test is now its detector.
